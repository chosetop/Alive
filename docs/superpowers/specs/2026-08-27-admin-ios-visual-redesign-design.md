# Alive Admin iOS 风格视觉重构设计规格

**日期：** 2026-08-27  
**状态：** 待规格审阅  
**范围：** `admin/` 后台应用的视觉系统、应用壳层和既有管理页面

## 1. 背景与目标

Alive 后台已经完成认证、内容管理、写作工作区和共享主题能力，但当前界面仍以早期的轻量管理台样式为主：页面之间的视觉关系较弱，操作控件密度和层级不够统一，写作场景与管理场景也没有共享一套明确的品牌语言。

本次工作将后台重构为 **Alive Writing Desk**：一张面向个人作者的数字写作桌。它需要同时满足两件事：

1. 让内容、分类和写作等操作更容易被识别和完成。
2. 让后台具有连续、克制、可长期使用的视觉个性，而不是通用 CRUD 模板。

本计划只改变表现层和交互呈现，不改变认证、路由、API 合约、数据模型、保存协议、发布规则或已有业务边界。

## 2. 用户与核心任务

**用户：** Alive 站点的个人作者/站主。  
**页面的单一任务：** 让作者打开后台后能立即知道“我在哪里、现在发生了什么、下一步最值得做什么”。

主要场景：

- 从 Dashboard 进入内容列表或开始写作。
- 在内容列表中按状态筛选、进入文章或创建文章。
- 管理分类并清晰区分编辑、删除和删除确认。
- 在写作工作区识别保存状态、目录、设置、发布和返回路径。
- 在移动端完成上述操作，不依赖精确点击或悬停。

## 3. 设计方向

### 3.1 视觉概念：Alive Writing Desk

后台采用“纸张底、玻璃控制层、墨水文字、单一活跃色”的桌面隐喻：内容区域保持安静和可读，导航与操作区域像叠放在纸面上的半透明控制卡片。玻璃效果只用于需要被识别为浮层或控制层的表面，正文和列表不大面积使用模糊，避免影响阅读和性能。

这不是通用的黑色霓虹仪表盘，也不是温暖奶油色编辑器：Alive 的辨识度来自写作工具语义、冷静的纸张灰和“光标”式活跃标记。

### 3.2 颜色令牌

颜色必须集中定义为语义令牌，组件不得散落硬编码色值。本次允许扩展主题变量，并允许为后台加入专属的应用层语义令牌；这些变量仍必须通过统一主题入口注入，不能在业务组件中自行维护颜色。

| 令牌 | 色值 | 用途 |
|---|---|---|
| `--c-paper` | `#F5F6F8` | 应用底色、阅读背景 |
| `--c-glass` | `rgba(255, 255, 255, 0.72)` | 顶栏、侧栏、浮层表面 |
| `--c-ink` | `#17202A` | 主文字、主要标题 |
| `--c-ink-muted` | `#718096` | 辅助文字、元数据 |
| `--c-alive` | `#5E6AD2` | 当前项、主操作、焦点和光标标记 |
| `--c-signal` | `#36A87A` | 已保存、已同步等正向状态 |

现有主题系统继续作为主题解析和持久化入口，但不再限制本次只能复用已有变量。可以新增 `--c-glass`、`--c-alive`、`--c-signal` 以及后台所需的表面、分隔、焦点和状态变量，并将它们纳入共享主题 manifest 与 CSS 变量输出。若主题已经提供同义令牌，则优先保留其变量名并通过应用层别名兼容。

「薰衣草」必须保留，且其展示名称、主题标识和前台现有行为不能被破坏。除此之外，本次可以新增主题，但每个新增主题必须有清晰的使用场景和完整的语义色映射，而不是只替换一个主色。建议最多新增两套，避免主题数量变成没有维护价值的色板集合。

### 3.3 字体与文字

- 正文和控件继续使用系统 UI 字体栈，优先匹配 Apple 平台的 San Francisco，并为非 Apple 平台提供系统无衬线回退。
- 页面标题使用同一 UI 字体的较大字号和更紧行高，不引入装饰性衬线字体，避免后台与前台阅读主题割裂。
- 数据、slug 和技术字段使用等宽回退字体，仅在确实表达机器可读值时使用。
- 文案保持现有中文语义，按钮使用动作词，例如“写一篇”“保存”“确认删除”；不为装饰新增模糊文案。

### 3.4 形状、层次与动效

- 控件和卡片采用 12–18px 的分级圆角；圆角表达容器层级，不给每个文本块加胶囊背景。
- 阴影使用低对比度、短扩散的叠层阴影；边框用于分隔和状态，不用重边框包住所有区域。
- 顶栏、移动抽屉、菜单和对话框可以使用半透明表面与背景模糊；正文列表和编辑画布保持清晰不透明。
- 交互反馈以颜色、背景和光标标记为主，动效只服务于抽屉/浮层出现、状态变化和导航反馈。
- 所有动效在 `prefers-reduced-motion: reduce` 下关闭或降为即时变化。

### 3.5 主题扩展原则

主题可以沿两个方向扩展：

- **薰衣草**：现有稳定主题，继续作为基线和回归对象；后台使用更清晰的玻璃层与紫色光标对比。
- **新增主题**：可围绕“夜间写作”“清晨纸张”或其他与 Alive 写作语境相关的完整氛围设计，但必须同时定义纸面、玻璃、墨色、弱化文字、强调色、成功色、危险色和遮罩色。

新增主题需要满足：在后台 Dashboard、内容、分类和写作工作区中均可正常显示；文字与交互状态保持可读；切换主题时不改变业务状态；前台若不消费该主题，不得影响前台默认主题和已有主题解析。

### 3.6 识别性元素：Alive 光标

整个后台只引入一个新的品牌性视觉动作：当前导航项、当前筛选项和主要保存状态共享一条短竖线光标标记。它可以表现为左侧 2–3px 的活跃线、状态旁的短竖线或焦点插入点，但必须承担真实状态提示，不能作为纯装饰重复使用。

## 4. 信息架构与布局

### 4.1 桌面端

```text
┌─────────────────────────────────────────────────────┐
│ Alive        当前空间 / 保存状态        用户头像     │
├───────────────┬─────────────────────────────────────┤
│  总览          │                                     │
│  内容          │  页面标题        主操作              │
│  分类          │                                     │
│  写作          │  玻璃卡片 / 列表 / 空状态            │
│               │                                     │
│  设置          │                                     │
└───────────────┴─────────────────────────────────────┘
```

- 顶栏固定承担品牌、当前上下文、保存状态和用户操作。
- 侧栏承担主导航；当前项同时使用背景、字重和 Alive 光标，不能只依赖颜色。
- 内容区使用有限阅读宽度，页面标题和主操作在同一视觉行，窄屏自动堆叠。
- 管理列表采用分组卡片或轻量行卡片，单行内保持标题、状态、元数据和动作的明确优先级。

### 4.2 移动端

- 侧栏变为可访问的抽屉或底部导航入口，不能继续压缩桌面侧栏。
- 顶栏和主要操作保留最小 44px 触控目标。
- 列表动作在空间不足时进入菜单，但删除确认仍保持清晰、可逆和可读。
- 页面不产生横向滚动；长标题、slug 和错误信息必须可换行或截断并保留完整可访问名称。

## 5. 组件与文件边界

### 5.1 共享层

- `admin/src/style.css`：应用级设计令牌、字体、全局基础、响应式和减少动效规则；允许声明后台专用的主题别名和状态变量。
- `admin/src/components/ui/ui.css`：按钮、图标按钮、菜单、弹层、toast 等基础组件的 iOS 风格呈现。
- `admin/src/components/ui/`：必要时扩展 `UiIconButton`、导航图标包装或状态标记；不得让业务组件直接依赖图标库实现细节。
- `packages/theme/`：如新增变量或主题，更新主题 manifest、CSS 输出和对应测试；保留「薰衣草」的展示名与标识。
- `admin/package.json`：如确认现有图标不足，引入 `lucide-vue-next`，并固定与当前 Vue/Vite 兼容的版本。

### 5.2 应用壳层

- `admin/src/layouts/AdminLayout.vue`：桌面侧栏、移动导航、顶栏、用户操作、当前路由上下文。
- `admin/src/layouts/WritingLayout.vue` 与写作组件：只重构外壳和视觉层，不重新设计已经确认的写作交互协议。

### 5.3 页面层

- `admin/src/views/Dashboard.vue`：欢迎区域、下一步入口和空内容提示。
- `admin/src/views/Entries.vue`、`admin/src/components/EntryRow.vue`：筛选、列表、状态、分页和主要操作。
- `admin/src/views/Categories.vue`、`admin/src/components/CategoryForm.vue`：列表、表单、错误与删除确认。
- 登录、404 等页面只做令牌和基础组件对齐，除非浏览器验收发现布局问题，不扩大为独立视觉项目。

## 6. 图标规则

允许引入 `lucide-vue-next` 作为线性图标库，原因是其笔画克制、尺寸一致、可通过 `aria-hidden` 与文字动作配合，适合 iOS 风格控制层。

- 图标只补充“看得懂的动作”，不能替换已有文字标签。
- 图标按钮必须使用 `UiIconButton` 或等价封装，并提供可访问名称。
- 同一动作在不同页面使用同一图标；禁止混用 emoji、Unicode 符号和多个图标库。
- 图标尺寸以 16px/20px 为主，触控区域不小于 44px。

## 7. 行为与可访问性约束

- 不改变现有路由名称、API 调用、认证判断、保存协调器、发布检查和错误映射。
- 所有可交互控件支持键盘操作；`:focus-visible` 必须有清晰的 Alive 色焦点环。
- 当前路由、当前筛选、保存状态和禁用状态不能只靠颜色表达。
- 浮层支持 Escape、外部点击（在现有组件契约允许时）和触屏路径；打开后焦点行为遵循现有 UI 组件测试约束。
- 加载、错误、空状态继续使用真实业务状态，不添加虚构统计或活动数据。
- 375px 宽度下无横向溢出，桌面宽度下内容列可读且不被拉成全屏表格。

## 8. 验收标准

### 视觉验收

- Dashboard、内容、分类、写作工作区共享同一套颜色、字体、圆角、阴影和状态语言。
- 顶栏/侧栏/浮层呈现 iOS 风格的层次，但正文和编辑画布仍然清晰、稳定、适合长期阅读。
- 当前导航、筛选和保存状态都能识别 Alive 光标，并且不依赖颜色单独传达。
- 「薰衣草」主题可正常选择、预览和保存；新增主题（如有）在后台四类主要场景中完成对比度、状态色和浮层层次验收。
- 页面在 1280px 和 375px 视口下均无横向滚动或明显控件溢出。

### 功能回归

- 登录、退出、路由守卫和会话恢复行为不变。
- 内容筛选、分页、进入编辑、分类增改删和删除确认行为不变。
- 写作工作区的保存、冲突、设置、发布和移动抽屉行为不变。

### 自动化与真实界面

- 为新增或改变的共享 UI 状态补充 Vitest 测试；优先测试语义属性、动作和响应式相关的可观察结果。
- 运行 `admin` 全量测试、类型检查和生产构建。
- 运行时在浏览器检查桌面宽度和 375px：登录后导航、内容列表筛选、分类表单、写作工作区、浮层/抽屉、键盘焦点和无横向溢出。
- 使用 `git diff --check` 检查文档和代码格式。

## 9. 非目标与边界

- 不新增后台业务能力、统计接口、搜索接口、权限角色或数据模型。
- 不重做前台 `frontend/` 页面布局；共享主题包可以新增变量和主题，但必须保持「薰衣草」及现有前台主题行为兼容。
- 不把写作工作区改造成新的编辑器，不改变 Plan 1/2/3 已完成的领域边界。
- 不引入完整设计系统框架或重量级组件库；只补足当前界面真正需要的图标封装和样式令牌。
- 不在本计划中实现媒体上传；媒体上传作为原有后续计划顺延。

## 10. 计划插入位置

本设计对应新增 **Plan 4：后台 iOS 风格视觉重构**。它排在现有 Plan 3「共享站点主题系统」之后；原 Plan 4「Aliyun OSS media upload」整体顺延为 Plan 5。实施计划生成后必须同步更新 `docs/superpowers/plans/2026-08-26-admin-writing-roadmap.md` 的执行顺序、跨计划契约和门禁说明，并在 `docs/progress.md` 记录本次设计、计划调整和后续验证结果。
